# VPS verification of a predeployment revision

This procedure is for Runr tickets whose acceptance requires the real VPS. The VPS systemd units execute files under `/opt/runr`; changing only the Render branch does not test those units. A ticket receipt is valid only when the host ran the exact tested revision on `predeployment/render-turso-r2` (or a documented ticket revision layered on it). Planned downtime for acquisition is acceptable. Do not claim a successful live test from local pytest, a branch label, or a Render deploy.

## Maintenance gate

The operator performs one VPS ticket at a time. Before changing the host, record in the ticket: permanent predeployment SHA and proof that the ticket's implementation commits are present in its tree; VPS `git -C /opt/runr rev-parse HEAD`, branch, `git status --porcelain`, current `systemctl cat` and enabled/active state for the acquisition services and timers, `/opt/runr/.venv/bin/python --version`, the active acquisition state pointer, and relevant state hashes. Record paths and fingerprints, never environment values or secrets. Verify a recoverable off-host checkpoint and sufficient disk space. A dirty checkout, missing checkpoint, unknown unit owner, mismatched Python, or absent tested commit stops the operation.

## Exact-revision test

1. Record a maintenance window and the previous checkout SHA, unit files and timer states as rollback targets. Stop and disable the LinkedIn, employer, publisher, cycle and export timers; stop their active services and wait until their locks are released. Include any acquisition worker that the live unit inventory shows can write the same state. Leave customer services running only if the planned test cannot affect them.
2. Fetch the permanent predeployment branch on the VPS. Verify the selected commit is reachable from it, verify the ticket commits or tree content, and check out that **exact commit** in `/opt/runr` while acquisition is stopped. Keep `.env`, `.env.acquisition`, provider credentials, and state outside Git untouched. If dependencies or unit files changed, apply only the reviewed requirements and units for that commit, run `systemctl daemon-reload`, and compare `systemctl cat` with the selected tree. Do not use `deploy/deploy.sh` as the test selector: it restarts `runr.target` and does not install updated unit files.
3. Run the ticket's bounded command through its actual systemd entrypoint with the approved request, concurrency, time and provider limits. For an offline check, keep live networking disabled. For an authorized live check, record the approval and provider budget first. Capture exit status, journal interval, receipt, exact Git SHA, source version, input/state hashes, and resource counters. A 300-second benchmark needs the full window; a state restore needs pre-switch, post-switch, canary, and rollback proof. Do not substitute a synthetic receipt for a live acceptance criterion.
4. Stop test services and demonstrate rollback. For ordinary benchmarks, restore the prior checkout SHA and any prior unit files, reload systemd, verify the original state pointer is unchanged, and restore the exact prior timer/service states. For RUN-45, demonstrate a switch back to the previous state generation, then decide the final active pair **together**: the tested code revision and validated restored state may remain active only as an authorized release; otherwise restore both the prior code and prior state pointer. Never leave new state active with old code without a compatibility check. Verify hashes, unit commands, pointer, and service health. Keep both state generations and all receipts. If rollback verification fails, leave acquisition stopped and record the incident; do not resume unattended timers.

For RUN-45, the state pointer switch is its actual recovery operation. Stage and validate a new version from the preserved checkpoint before switching; never overwrite the prior state. RUN-36 and RUN-56 should use a copy or isolated test state where feasible and must not alter the authoritative active pointer. Run these host tests serially because they share `/opt/runr`, systemd units, producer state, and provider budgets.

## Ticket and merge evidence

The ticket must contain the tested commit, permanent predeployment integration revision, host revision before/during/after, actual unit command, state/input fingerprint, test window and limits, exit status, sanitized receipt, rollback result, and any remaining blocker. `Predeployment Integrated` requires verified code integration and combined checks; `Ready for Production` additionally requires the ticket's live acceptance evidence. A failed or unavailable VPS run does not retroactively erase a valid code integration, but it cannot be reported as live verification.
