# VPS verification of a predeployment revision

The acquisition systemd units execute `/opt/runr/deploy/*`. A Render branch switch does not select VPS code. On 2026-09-22 the live VPS was reachable through the operator's `runr-vps` SSH alias: `/opt/runr` was a **plain deployed directory without `.git`**, Python was 3.12.7, the LinkedIn/employer/publisher timers were enabled and active, and `/srv/runr/state/active` was a symlink. The employer unit's most recent exit was 124. The commit in `deploy/vps-runtime-contract.json` is a declared pin, not proof of the files actually installed. Do not run `git -C /opt/runr` or `git checkout` there.

## Preflight and exact code identity

1. From a trusted local Git checkout, fetch `origin/predeployment/render-turso-r2`. Verify the ticket's tested commit is an ancestor of the selected permanent predeployment SHA, or compare the ticket's changed paths when a squash was used. Export that **exact SHA** with `git archive`; record the SHA-256 of the archive and a manifest of relevant tracked file hashes. Transfer the archive and manifest to a new root-owned VPS staging directory outside `/opt/runr`. Verify the archive hash on the host before extraction. Do not take code from an uncommitted worktree or a moving branch name.
2. On the host, record the current `/opt/runr` code-file hashes, effective `systemctl cat` and enabled/active timer/service states, Python version, state pointer and hashes, free disk, and off-host checkpoint. The current release SHA is **unknown** unless an independent signed release record matches the installed file hashes. Record environment **file paths**, never values or secrets. A missing backup, insufficient disk, unexpected active writer, or failed checksum stops the run.
3. Extract into the staging directory and verify its files against the manifest. Keep the current `.env`, `.env.acquisition`, optional provider file, `.venv`, untracked runtime inputs, and `/srv/runr` state intact. Identify every runtime-only path needed by the selected entrypoint; link or copy it into staging with the same owner and permissions. Verify the staged Python interpreter is 3.12.7 and run offline validation/help commands before switching any service. Never copy secrets into Linear or a Git artifact.

## Serialized maintenance run

1. Reserve one acquisition maintenance window. Stop and disable competing LinkedIn, employer, publisher, cycle and export timers, then stop active acquisition services and wait for the source/publisher locks to clear. Include any live acquisition worker that can write the same state. Record the exact prior state so it can be restored. A read-only inspection ticket does not need this stop.
2. Preserve the entire old `/opt/runr` directory as the rollback target. Activate the staged release under the fixed `/opt/runr` path only after the staged tree, runtime-only links, ownership, unit files, and dependencies have been verified. Use a reversible directory/symlink switch; do not overlay or `rsync --delete` onto the current directory. Reinstall only reviewed unit definitions when the selected revision changes them, then `systemctl daemon-reload` and compare the effective `ExecStart` and sandbox properties. `deploy/deploy.sh` is not a release selector: it restarts `runr.target` and does not install changed units.
3. Run the bounded ticket command through the installed systemd entrypoint, with approved provider budget, request/concurrency/time limits and, where possible, isolated state/export/receipt paths. Record the staged archive hash and selected Git SHA in the receipt alongside actual unit command, journal window, exit code, source/input/state hashes and resource counters. A 300-second benchmark must complete its full window. A RUN-45 restore requires pre-switch, post-switch, canary and rollback evidence. A temporary test receipt is not a production release receipt.
4. Stop test services and prove rollback. For a benchmark, switch `/opt/runr` back to the preserved directory, restore prior unit files and timer/service states, and verify its original file hashes and active state pointer. For RUN-45, demonstrate a switch back to the previous state generation; leave the new code/state pair active only through an authorized release, otherwise restore both old code and old state together. Keep both state generations and receipts. If any rollback check fails, keep acquisition stopped and record the incident rather than restarting unattended timers.

RUN-36 and RUN-56 should test against copied or isolated producer state and must not switch the authoritative pointer. RUN-45 owns the real state activation. Host tests run serially because they share `/opt/runr`, systemd units, state, catalog writes and provider budgets. Read-only RUN-32 inspection can use the currently installed files without selecting a new release, provided the report identifies that tree by hashes rather than an unverified commit claim.

## Ticket gate

The ticket must contain the tested commit, permanent predeployment integration SHA, archive hash, host file hashes before/during/after, effective unit command, state/input fingerprint, test window and limits, exit status, sanitized receipt, rollback result and any remaining blocker. `Predeployment Integrated` requires verified code integration and combined checks. `Ready for Production` additionally requires the ticket's live acceptance evidence. An unavailable or failed host run leaves live verification pending; it does not erase a valid code integration.
