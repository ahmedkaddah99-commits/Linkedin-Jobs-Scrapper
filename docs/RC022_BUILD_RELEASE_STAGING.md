# RC-022 build, release, and staging contract

Status: implemented and verified offline on `deployment/render-turso-r2`.

This contract separates the static frontend release from the API and worker
runtime images. It does not claim that any Render service, VPS worker, Turso
schema, or staging environment has been deployed.

## Release identities

Every runtime image carries OCI labels for service, branch, commit, and
`runr-contract-v1`. At runtime, `deploy/start.sh` emits one redacted JSON
record from `backend.deployment.release_contract` before starting API, worker,
process-next, or migration work. Commit and branch precedence is:

1. explicit `RUNR_RELEASE_COMMIT` / `RUNR_RELEASE_BRANCH`;
2. Render's `RENDER_GIT_COMMIT` / `RENDER_GIT_BRANCH`;
3. `unknown` (which is visible and is never presented as a real revision).

The static frontend build writes `runr-release.json` into `dist/` with the same
schema. It is generated by `frontend/scripts/write-release-metadata.mjs` and
is ignored as a build artifact.

The stable compatibility protocol is `runr-contract-v1`. API/worker versions
may change implementation versions while this protocol remains stable. A
client or worker with another protocol is not admitted as a compatible mixed
version. The current migration head is recorded as
`058_customer_task_queue`.

## Image boundaries

| Release | Build file | Runtime command | Static frontend build | Runtime dependencies retained |
|---|---|---|---|---|
| Frontend | Render static service | `npm run build` | Yes, once | Vite/React only |
| API | `Dockerfile.api` | `./deploy/start.sh api` | No | Python, Node, Chromium, OCR, LibreOffice, document parsers |
| Worker | `Dockerfile.worker` | `./deploy/start.sh worker` | No | Python, Node, Chromium, OCR, LibreOffice, document parsers |

The API and worker Dockerfiles intentionally retain browser/OCR/office
dependencies. Route tracing found current API compatibility routes that import
document extraction and tailored-document rendering, while workers execute CV
processing, PDF conversion, rendered career fallbacks, and document stages.
The API image can only lose those dependencies after route extraction proves
those paths are unreachable in the selected API contract.

Neither runtime Dockerfile copies `frontend/dist` or runs `npm run build`.
Both copy only the frontend renderer script and its source modules required for
server-side CV PDF rendering. The worker additionally copies `scripts/` for
acquisition entrypoints. Both run as non-root user `runr`.

The root `Dockerfile` remains only as a compatibility image for existing local
consumers; it also no longer builds the static frontend. Production Render and
CI release jobs must use the explicit API/worker Dockerfiles below.

## Render build-filter matrix

The `buildFilter.paths` entries in `render.yaml` are the deployment source of
truth:

| Change | Frontend | API | Worker |
|---|---:|---:|---:|
| `frontend/src/pages/**`, normal frontend UI | rebuild | no | no |
| `frontend/src/lib/api.js` | rebuild | no | no |
| CV renderer source/script or frontend package lock | rebuild | rebuild | rebuild |
| `backend/**` or `workspace_runner.py` | no | rebuild | rebuild |
| `scripts/**` | no | no | rebuild |
| `Dockerfile.api` | no | rebuild | no |
| `Dockerfile.worker` | no | no | rebuild |
| `requirements-linux.txt`, `deploy/start.sh` | no | rebuild | rebuild |
| `render.yaml` | rebuild | rebuild | rebuild |
| docs/tests only | no | no | no |

This means a normal frontend-only commit does not restart either runtime
worker. Shared backend, renderer, dependency, startup, or deployment-contract
changes rebuild every affected runtime. `render.yaml` deliberately fans out to
all services because service definitions and environment isolation are shared.

The mapping is also exposed as the testable public function
`backend.deployment.release_contract.affected_services`.

## Migration ownership and ordering

Only the API service's pre-deploy command runs migrations. The worker image has
no migration command and must not independently advance the schema. The
designated release owner records and applies the contiguous registry in order:

```text
054_company_identity_reconciliation
055_acquisition_analytics_indexes
056_phase_a_scheduler_fencing
057_phase_e_intelligence_recovery
058_customer_task_queue
```

The owner must verify that the previous API/worker version can read the schema
before enabling new writers. Rollback is image/task ownership rollback, not a
destructive database downgrade or restoration of an old database over newer
customer writes.

## Staging contract

An RC-022 staging environment must use distinct names and credentials for all
of the following:

- Render/API service and worker service;
- Turso database or isolated staging namespace;
- acquisition/customer queues and worker IDs;
- R2 bucket or prefix and signed-download policy;
- billing, email/OAuth, Clerk, ScrapeOps, DeepSeek, and analytics targets;
- release branch/commit metadata and migration head.

Preview services must not consume production queue rows, object keys, customer
documents, billing events, email recipients, or analytics streams. The staging
worker must use a staging `WORKER_ID`, `WORKER_ROLE`, and release contract, and
its input/state mounts must be explicit. No production secret may be copied to
the staging environment merely because a variable has the same name.

Required mixed-version checks are:

1. Start the previous compatible API/worker contract against the current
   backward-compatible schema.
2. Start the new API with the previous compatible worker and verify queue
   claim, task status, artifact descriptor, and signed-download response.
3. Start the new worker with the previous compatible API and verify customer
   task and acquisition-role claims remain disjoint.
4. Confirm a frontend-only build changes only the static release metadata and
   does not restart either worker.
5. Confirm an incompatible contract version is rejected by the compatibility
   check before any task claim.

## Release and rollback sequence

1. Select a committed branch revision and record its commit, branch, image
   digests, manifest hash, migration head, and environment names.
2. Build and publish the static frontend, API image, and worker image from the
   same selected commit. Do not build a worker from another dirty worktree.
3. Run the API migration owner once, then start API and role-scoped workers
   with heartbeats and unique IDs. Enable frontend flags only after worker/API
   compatibility is verified.
4. Run staging health, queue claim, lifecycle, artifact signed-download, and
   frontend release checks. Keep deployed revisions separate from branch
   evidence.
5. For rollback, stop new claims, fence/drain the affected role, restore the
   last compatible image and task ownership, and keep immutable object-storage
   artifacts. Never use a destructive Git reset/clean or database downgrade.

For the VPS/systemd path, `deploy/deploy.sh` installs the selected backend
requirements and restarts API/worker services without implicitly pulling Git or
building the frontend. `runr-api.service` and `runr-worker.service` use
`deploy/start.sh`, so the same release metadata is emitted locally as in the
container path. The static frontend is a separate explicit build/restart.
