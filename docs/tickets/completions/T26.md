## Static evidence captured in this implementation

### 1. VPS unit/timer ownership and command lines

| Unit / Timer | User/Group | ExecStart / Unit | Schedule |

All three producer/publisher units:

- are `PartOf=runr.target`;
- are `WantedBy=multi-user.target`;
- use the same hardened sandbox (`ProtectSystem=strict`, `NoNewPrivileges=true`, `RestrictAddressFamilies=AF_UNIX AF_INET AF_INET6`, etc.);
- load `/opt/runr/.env.acquisition` (the acquisition env boundary, not the customer `.env`).

The legacy `runr-acquisition-worker.service` is intentionally **not** in `runr.target` (C6).

### 2. Intended Turso/libSQL and release binding

- `.env.acquisition` example declares `DATABASE_BACKEND=turso`, `TURSO_DATABASE_URL`, and `TURSO_AUTH_TOKEN` placeholders.
- The three acquisition units therefore bind to the Turso-backed catalog when deployed.
- `render.yaml` declares `DATABASE_BACKEND: turso` for both `runr-api` and `runr-worker`.
- All three Render services declare `RUNR_RELEASE_BRANCH: deployment/render-turso-r2` and `RUNR_RELEASE_CONTRACT_VERSION: runr-contract-v1`.
- The VPS acquisition wrappers (`run-acquisition-source.sh`, `run-acquisition-publisher.sh`) forward `RUNR_SOURCE_VERSION` as the release commit / source version, so the intended VPS release SHA is the value set in `.env.acquisition`.

### 3. Checkpoint-table schema evidence

The publisher script (`scripts/publish_producer_states.py`) creates `acquisition_publisher_checkpoints` with columns:

- `source` (PRIMARY KEY)
- `source_rowid`
- `source_watermark`
- `bootstrap_complete`
- `last_cycle_id`
- `last_publication_id`
- `updated_at`

The static test `test_publisher_creates_checkpoint_table_with_expected_columns` verifies this schema.
